scenariuszy zamrożonego EXP oraz odtworzenie raportu z SQLite.** Nie wykonano

To postęp AJ-07, nie ukończenie całego systemu i nie kwalifikacja strategii.

## Zmiana

- `run weekly-recorded`: dokładny EXP i jego wersja, przypięte STRAT/DATA,
  wszystkie scenariusze z planu; bez wyboru korzystnego wariantu i bez importu
  dowolnego raportu jako wyniku obliczeń.
- Jeden RUN na scenariusz, EVENT każdego RUN oraz manifest serii. Zapis jednej
  transakcji SQLite: wszystko albo nic. Awaria zapisu nie zostawia części serii.
- Klucz idempotencji wiąże pełne wersje rekordów, lokalizację CSV i autora.
  Powtórzenie ukończonego żądania odczytuje oryginalną serię; konflikt nie
  nadpisuje historii. Równoległe wywołania mogą wykonać obliczenia, ale nie
  zapiszą dwóch serii z tym samym kluczem. To nie gwarancja jednego użycia CPU.
- Przed zapisem sprawdzane są ponownie hashe wejścia, kodu i zamrożonych
  rekordów. Wymagany jest aktualny schemat 7 i obecność sześciu triggerów
  ochrony historii. Polecenie nie inicjalizuje ani nie migruje bazy. Kontrola
  nazw triggerów nie jest pełnym audytem ich definicji lub odporności na
  administratora, który ma prawo zmieniać SQLite.
- `run weekly-export` odtwarza cały oryginalny raport z przypiętych RUN,
  sprawdza manifest i hashe, zapisuje wyłącznie nowy plik. Nie potrzebuje CSV,
  nie przelicza modelu i nie dopisuje rekordów. Działa z istniejącym Analytics.
- Pełne IS/OOS strategii i benchmarku, sygnały, realizacje, gotówka, jednostki
  i krzywe pozostają w `reproduction.weekly_result`. Integralność obejmuje
  również projekcje pól RUN i pełny benchmark, nie tylko wybrane metryki.

Nowe pliki: `application/weekly_recorded.py`, `lab/weekly_run.py`, test integracyjny
oraz `scripts/check_weekly_site_contract.mjs`. Zmieniono CLI, wspólny zapis rekordu,
kontrolę reprodukcji i manifest fingerprintu adaptera. Zmiana fingerprintu wymaga
nowej wersji zamrożonego planu; nie podmieniamy hashu wcześniejszego EXP.

## Znaczenie wyniku

- RUN ma typ `BACKTEST`, stan techniczny `completed`, wynik **`inconclusive`**.
  Kryteria pozostają `not_evaluated`. Nie nadajemy automatycznie `passed` ani
  `verified`; próba zmiany etykiety bez zgodnego kontraktu jest wykrywana.
- Główne `RUN.metrics` opisują **OOS strategii**. `RUN.total_cost` opisuje
  **pełny okres strategii w jednym scenariuszu**; nie jest kosztem AI, taryfą
  brokera ani sumą strategii i benchmarku. Pełne zakresy są w artefakcie.
- Flagi oryginalnego raportu offline (`records_written=0`,
  `run_record_created=false`) opisują samo obliczenie, zanim powstały RUN.
  Pozostają niezmienione dla zachowania hashu i kompatybilności. Zapis serii
  potwierdza osobna odpowiedź `weekly-recorded-v1` i manifest EVENT.
- Ponowienie klucza po udanym zapisie to **odczyt historycznego wyniku**,
  nie potwierdzenie aktualnego CSV lub kodu. Nowe obliczenie wymaga nowego
  klucza i ponownych kontroli przypiętego planu. Nie kopiuj danych testowych
  do rejestru rzeczywistych badań.
- Dwa odtworzenia tego samego scenariusza można porównać; różnych scenariuszy
  nie traktujemy jak reprodukcji. Dotychczasowy REVIEW wymaga dalszej oceny
  kryteriów i niezależnych dowodów; tygodniowe RUN nie uzyskują `verified`.
