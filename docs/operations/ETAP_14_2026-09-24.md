## Odtworzone usterki

- Ten sam RUN mógł uchodzić za dwa niezależne przebiegi.
- Przekazany `ReproductionReport(True)` mógł przesłonić różnice w danych; CLI
  porównywał tylko pierwsze dwa RUN i pomijał trzeci.
- Brak hashy oraz pusty kontrakt metryk mogły dawać pozorną zgodność.
- NaN powodował wyjątek, a nieskończona tolerancja przepuszczała różnice.
- Nie sprawdzano dokładnego powiązania każdego RUN z wersją EXP, statusu
  technicznego i integralności wyjścia.
- Zaokrąglenie Decimal mogło obniżyć różnicę przekraczającą tolerancję do granicy
  dopuszczalnej wartości.
- Idempotencja mogła zwrócić poprzedni REVIEW po zmianie wniosków i wejść.
- Historyczna etykieta `verified` nie dowodziła istnienia niezależnej kontroli;
  status i nowa decyzja ryzyka mogły sugerować dalszy awans.
- Wstępna wersja poprawki sprawdzała flagi zbiorcze, nie spójność zagnieżdżonych
  ocen. Osobny test odtworzył cztery takie sprzeczności; również je naprawiono.

Pierwszy pakiet testów negatywnych przed implementacją: 12 niepowodzeń i 4 błędy.
Późniejsze testy tolerancji i idempotencji również najpierw odtworzyły błędy.

## Wdrożone lokalnie

- Każdy RUN ma sprawdzane powiązanie, status, czas, błędy, koszt, metryki i hashe
  legacy kontraktu wyjściowego. Wszystkie kolejne RUN są porównywane z pierwszym.
- Jawny raport `astraljet-independent-check-v1` zawiera obserwacje kontrolne,
  metodę, autora, wersję implementacji oraz dokładne referencje RUN/EXP.
- Import JSON: ograniczony rozmiar/liczba, brak dodatkowych i powtórzonych pól,
  sprawdzenie hashy i skończonych wartości; brak wykonywania treści raportu.
- Brak raportu lub niespójność daje `unverified`; jawne odrzucenie `rejected`.
  Powtórzenie tego samego silnika jest odtwarzalnością, nie osobną metodą.
- REVIEW zachowuje kopię artefaktu, szczegóły porównań, wersje i pełne hashe
  rekordów oraz hash żądania. Dane są odczytywane w jednej transakcji SQLite.
- Identyczne ponowienie zwraca ten sam rekord; zmienione argumenty albo klucz
  innego typu rekordu są odrzucane, bez zmiany wcześniejszej historii.
- RISK-DECISION ponownie sprawdza spójność zapisanego pakietu. Stary REVIEW bez
  pakietu nie kwalifikuje się do nowej decyzji `allowed`. Status ujawnia blokadę.
- Pole `verification_details` jest opcjonalne dla odczytu starych rekordów.
  Brak nowej migracji SQL; historia nie jest przepisywana.

## Granice i dalszy zakres

Hash potwierdza spójność, nie tożsamość autora. Operator musi dostarczyć
autentyczne obliczenie kontrolne; inna nazwa i inny hash nie dowodzą, że program
rzeczywiście uruchomiono. Ta ścieżka korzysta z zapisanych rekordów i istniejącego
kontraktu legacy RUN, nie przelicza wejściowego CSV i nie zastępuje audytu
metody, przyszłych informacji, doboru kosztów ani zatwierdzenia parametrów.

Nie powstał adapter `weekly-offline-report-v1` → RUN, niezależny silnik dla
rzeczywistej strategii ani podłączenie tej oceny do workera witryny. P006–P010
pozostają otwarte. Nie zmieniano cen/kosztów, polityki ryzyka, budżetu,
rachunków, mandatów, MT5, działających turnusów DEMO ani LIVE. Historyczne
decyzje i mandaty pozostają bez zmian; poprawka dotyczy nowych ocen/decyzji.

Pełna gotowość AJ-00–AJ-18 pozostaje niepotwierdzona. Następny dowód odbioru
to rzeczywisty, zatwierdzony i zamrożony eksperyment z niezależnym raportem,
nie kolejna syntetyczna etykieta `verified`.
